## Инструменты

### GitLab CI и Jenkins

Два главных инструмента для CI/CD, у каждого свои особенности.

**Jenkins** чаще можно встретить в старых проектах, либо в закрытых инфраструктурах, свойственно для банков, например.

**GitLab CI** активно набирает популярность + очень много где уже используется, в целом всё новое тоже стартует именно на нём. С точки зрения использования гораздо проще Jenkins'а.

---

## GitLab CI

### Минимум:

- Понимать что такое **pipeline, stage, job**
- Написать `.gitlab-ci.yml` с парой стейджей (build, test, deploy)

### База:

- `only/rules` - когда job запускается, а когда нет
- `variables` - переменные на уровне pipeline/job
- **CI/CD Variables** в настройках проекта (секреты)
- `cache` - кэширование зависимостей между запусками
- `before_script` / `after_script`
- `artifacts` - передача файлов между job'ами
- Сборка и пуш Docker-образов в GitLab Registry
- Работа с разными окружениями (environments)
- `when` - ручное подтверждение деплоя

### Хорошо:

- `needs`
- `extends` и **YAML-якоря** - переиспользование конфигов
- `include` - шаблоны из других файлов/репозиториев
- `trigger` - запуск пайплайна в другом проекте
- **GitLab Runner** - установка, настройка, типы executor'ов (shell, docker, kubernetes)

## Jenkins

### Минимум:

- Понимать архитектуру: **Jenkins Master + Agent**
- Запустить shell-команду, посмотреть логи
- Понять что такое **build trigger** (ручной, по webhook, по расписанию)

### База:

- **Jenkinsfile**
- Декларативный пайплайн: `pipeline`, `agent`, `stages`, `stage`, `steps`
- `post` - действия after success/failure/always
- `environment` - переменные
- **Credentials** - хранение секретов (SSH ключи, пароли, токены)
- `parameters` - параметризованные сборки
- Интеграция с Git (webhook от GitLab/GitHub)

### Хорошо:

- Скриптовые пайплайны на **Groovy**
- **Shared Libraries** - переиспользование кода между пайплайнами
- **Параллельные стейджи**
- `when` - условное выполнение
- `input` - ручное подтверждение (аналог `when: manual`)
- **Multibranch пайплайн** - автоматический pipeline по веткам
- **Agent на Docker** - каждый билд в чистом контейнере

# CI/CD - Практика и Собесы

## Практика

Лучше всего знакомиться с CI/CD на основе **GitLab CI** — вся практика рекомендована к нему.

---

### Написать пайплайн

Написать простой пайплайн для приложения, которое было в линуксе, а затем в докере.

**Три стадии:**

- **Build**
  - Собрать Docker-образ из Dockerfile
- **Test**
  - Линтер: flake8 (Python), eslint (JS) и т.д.
- **Deploy**
  - SSH на сервер → обновить контейнер

---

### Усложнить

**Варианты:**

**1. Пайплайн с тестами и окружениями, три окружения:**
- `dev` (деплоится автоматически по пушу в ветку)
- `staging` (автоматически по мерджу в main)
- `prod` (только manual)

Между стейджами передавать артефакты, использовать переменные окружения из CI/CD Settings для секретов. Добавить кэширование зависимостей.

**2. Шаблон CI для нескольких проектов.**
Создать отдельный репозиторий с общими шаблонами, подключать через `include`.

Один шаблон для Python-проектов, другой для Node.js, третий для Go. Каждый проект подключает нужный шаблон и переопределяет только переменные.
